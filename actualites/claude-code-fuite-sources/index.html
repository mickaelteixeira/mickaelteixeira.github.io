Une source map ouvre le capot de Claude Code. L’erreur de publication sur npm expose le code client et révèle des fonctions internes.

Le 31 mars 2026, une livraison de Claude Code sur npm expose du code interne. Une source map donne accès aux coulisses du client en ligne de commande d’Anthropic.

Un fichier de débogage dans une livraison npm, et le code interne de Claude Code devient lisible. Le 31 mars 2026, l’agent en ligne de commande d’Anthropic se retrouve ainsi au centre des analyses. Ce qui me frappe, c’est le point de départ de l’incident : un fichier qui accompagne le programme distribué.

Une source map d’environ 60 Mo.

Le chercheur Chaofan Shou signale une source map dans la version 2.1.88. Ce type de fichier relie le programme transformé pour sa distribution à son code d’origine. Les analyses décrivent ici un fichier d’environ 60 Mo, contenant du TypeScript et faisant aussi référence à une archive.

Le code exposé est celui du client : le programme qui dialogue avec le modèle et organise ses outils. Les modèles Claude, leurs données d’entraînement et l’infrastructure backend sont d’autres parties du système. C’est l’assemblage de l’agent que cette publication permet d’examiner.

Undercover vise les contributions internes.

Anthropic indique qu’aucune donnée sensible de clients ni aucun identifiant d’accès n’ont été exposés. Pour moi, l’intérêt technique de cet incident tient aux fonctions internes qui apparaissent dans les analyses et à la manière dont elles s’insèrent dans le client.

Parmi elles, le fichier Undercover décrit des instructions pour les versions internes d’Anthropic lors de contributions publiques. Elles visent à éviter la divulgation d’informations internes et prévoient le retrait des mentions d’attribution à l’IA. C’est un aperçu des consignes associées à ces contributions.

Regarder le paquet avant de le livrer.

Le point qui me paraît transposable à nos propres outils, c’est le contenu du paquet livré. La documentation npm permet de définir un champ files dans package.json pour sélectionner les fichiers à inclure. Pour une petite bibliothèque dont la sortie JavaScript est dans dist, on peut par exemple limiter cette sélection aux fichiers JavaScript. Voici un exemple à adapter à la structure réelle du projet.

Ce choix laisse les fichiers .map hors de cette sélection. npm prévoit toutefois des fichiers toujours inclus, notamment package.json, le README, la licence et les fichiers désignés par main ou bin. Je regarderais donc le paquet obtenu avant d’en conclure que la sélection répond au besoin. Une règle écrite dans la configuration et le contenu réellement distribué sont deux choses que je veux rapprocher.

Relire ce qui part.

Avant une livraison, je veux regarder la liste des fichiers du paquet. C’est un contrôle concret, à faire sur le résultat de la préparation, avec une attention particulière aux fichiers de débogage.

Cette lecture devrait suivre le chemin de livraison. Si le paquet est préparé après une compilation, c’est à cet endroit que je voudrais examiner les fichiers. Mon objectif serait simple : retrouver les éléments nécessaires à l’usage prévu et comprendre la présence de chacun des autres. Un fichier de débogage peut être utile dans un contexte donné ; sa diffusion devrait correspondre à une décision explicite.

C’est aussi ce qui rend l’incident intéressant au-delà de Claude Code. Le problème de départ tient à la frontière entre ce qui aide à construire un programme et ce qui doit accompagner sa distribution. J’y vois une bonne raison de donner à cette frontière une étape de revue à part entière. Le contenu final du paquet mérite autant d’attention que le code que l’on vient de modifier.

Buddy et Kairos apparaissent dans le code.

Les analyses repèrent aussi Buddy, un compagnon virtuel, et Kairos, un mode d’assistant persistant avec consolidation de mémoire. Ces éléments donnent un aperçu de fonctions internes. À cette date, leur présence dans le code ne donne pas de calendrier de disponibilité publique.

J’aime comprendre comment un agent est assemblé : le client, les outils qu’il organise et les consignes qui l’accompagnent. Cette publication involontaire en laisse voir une partie. L’ironie est assez forte pour Anthropic, qui dévoile ainsi davantage de son fonctionnement qu’il ne l’avait prévu. Cette exposition involontaire du code ne constitue pas une ouverture du logiciel. Le code exposé offre un aperçu technique ; pour les fonctions publiques, j’attends les annonces de produit.
