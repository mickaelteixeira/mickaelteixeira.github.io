Génériques PHP et TypePHP, deux pistes à suivre. Le vote reste ouvert sur la RFC, tandis que le compilateur de Swoole explore le code natif.

Les génériques font débat dans PHP, et TypePHP explore la compilation native. J’attends surtout de voir les garanties et la compatibilité dans des applications réelles.

Les génériques dans PHP et la compilation native avec TypePHP touchent à deux sujets que j’ai envie de suivre. Le premier concerne une proposition pour le langage. Le second explore une autre façon d’exécuter du code. Au 17 juin 2026, je regarde ces deux pistes avec la même attente : comprendre ce qu’elles apportent à une application réelle.

Une proposition de génériques encore au vote.

Le vote sur la RFC Bound-Erased Generic Types a commencé le 14 juin et doit se terminer le 28 juin. Il est donc encore ouvert. Dans les échanges, certains votants souhaitent des génériques tout en refusant cette proposition. Le choix de l’implémentation fait pleinement partie du débat.

Les génériques permettent de décrire un type paramétré par un autre. Une collection peut ainsi préciser le type de ses éléments. La RFC propose un effacement vers les bornes déclarées à l’exécution. Elle combine plusieurs contrôles avec le travail des outils d’analyse statique.

Cet exemple donne une idée de ce que l’on cherche à exprimer. Le paramètre T relie le type de la valeur reçue à celui de la valeur renvoyée. La fonction ne se contente donc pas d’annoncer une sortie générale : la proposition permet de décrire une relation entre l’entrée et la sortie. C’est cette relation qui m’intéresse quand je pense aux collections et aux fonctions que je voudrais rendre plus faciles à comprendre.

Pour évaluer cette syntaxe dans un projet, je partirais d’un exemple assez petit pour pouvoir suivre les types à la main. Une valeur entre, passe par une collection puis ressort. Je voudrais savoir ce que le langage contrôle et ce que l’analyse statique doit encore établir. Cette répartition me paraît plus importante que l’apparence de la déclaration. Elle détermine les erreurs que je peux espérer repérer avant l’exécution.

Lire cet extrait comme une proposition.

Cette syntaxe appartient à la RFC. Je ne la copierais pas dans une application PHP courante comme une fonction déjà disponible. Elle sert ici à comprendre ce que la proposition veut permettre d’écrire.

C’est sur ces garanties que je veux juger une nouvelle syntaxe. Comment les types sont-ils contrôlés, et à quel moment ? Ce sont des questions concrètes pour le code que l’on écrit. La discussion autour de cette RFC porte sur une proposition précise ; le calendrier de futurs génériques natifs reste ouvert.

TypePHP passe par la compilation.

TypePHP, le projet de Swoole, se présente comme un compilateur AOT, pour Ahead-Of-Time. Il passe par une génération de C++ avant de produire du code machine natif. Cette piste de compilation me donne envie de voir ce qu’elle permet sur une application.

J’attends des essais reproductibles. Pour moi, un résultat sur un calcul isolé apporte moins qu’une mesure sur une application Symfony ou Laravel. Je veux comprendre le gain dans ce contexte, avec ses dépendances et les comportements dont elle a besoin au quotidien.

La compatibilité décidera de mon choix.

L’objectif de compatibilité avec l’écosystème est important. Pour envisager une migration, je voudrais surtout savoir comment le code existant se comporte. Les dépendances utilisées par l’application doivent entrer dans l’évaluation, au même titre que les performances.

Du côté de TypePHP, mon premier essai souhaité serait tout aussi modeste. Je choisirais une portion d’application identifiable, avec ses entrées et son résultat attendu, puis j’examinerais le parcours de compilation et les dépendances utilisées. Je voudrais pouvoir refaire la mesure et comprendre les écarts. Un changement d’exécution devient intéressant pour moi quand je sais décrire ce qu’il améliore et ce qu’il demande en échange.

Cette façon de procéder laisse de la place à l’envie d’expérimenter. Je n’ai pas besoin de choisir immédiatement un camp pour suivre les deux projets. Je veux surtout garder les questions de typage et celles de compilation assez claires pour pouvoir apprendre quelque chose de chaque essai.

J’ai donc hâte de voir des applications réelles mises à l’essai avec TypePHP. Côté PHP, je suivrai le résultat du vote et les discussions sur les garanties de types. Ces deux pistes se jugeront sur ce qu’elles permettent de faire concrètement. C’est là que se décidera mon envie de les utiliser dans un projet.

Et depuis

Le vote s’est clos le 28 juin 2026. La RFC a été rejetée, avec 7 voix pour, 19 contre et 10 abstentions.
