Accueil / Actualités / IA et métier

8 janvier 2026 · 4 min de lecture · par Mickaël Teixeira

Tailwind gagne des utilisateurs, perd des revenus. Le témoignage d’Adam Wathan met le financement de l’open source au cœur du sujet.

Adam Wathan annonce le licenciement de 75 % de son équipe d’ingénierie chez Tailwind Labs. Son récit montre un décalage brutal entre popularité et financement.

Le message d’Adam Wathan me fait l’effet d’une douche froide. À l’origine de Tailwind CSS et dirigeant de Tailwind Labs, il décrit un framework qui gagne en popularité et une entreprise dont les revenus reculent. Le succès de l’outil et les moyens de le maintenir prennent des directions opposées.

75 % de l’équipe d’ingénierie licenciée.

Dans son commentaire GitHub du 7 janvier 2026, Wathan annonce que 75 % de son équipe d’ingénierie a perdu son emploi la veille. Il décrit un trafic vers la documentation inférieur d’environ 40 % à celui du début de 2023, et des revenus en baisse de près de 80 %.

Il affirme pourtant que Tailwind continue de gagner en popularité. C’est ce contraste qui me préoccupe. L’outil est utilisé, mais le travail de ceux qui le construisent et le maintiennent doit toujours être financé. La popularité ne suffit pas à payer ce travail.

La documentation faisait découvrir les produits.

Wathan explique que la documentation est le canal par lequel les utilisateurs découvrent leurs offres commerciales. Selon lui, les assistants d’IA bouleversent ce parcours. Un développeur peut obtenir de l’aide pour utiliser Tailwind sans passer par les pages où sont présentés les produits payants.

C’est un mécanisme assez troublant. L’assistant facilite l’utilisation des classes CSS. Dans le même temps, ce parcours peut éloigner l’utilisateur des offres qui financent leurs créateurs. Je trouve difficile d’ignorer cette tension entre l’aide immédiate que l’on reçoit et le travail nécessaire pour que l’outil continue d’exister.

Un petit exemple rend ce parcours très concret. Dans Tailwind, le préfixe hover: permet d’appliquer une classe au survol. On peut donc exprimer la couleur de fond d’un bouton et sa variation directement dans le HTML. Voici un exemple minimal que j’écris pour montrer cette syntaxe, dans une page où Tailwind est déjà chargé.

Obtenir ces quelques caractères dans une réponse d’assistant est très pratique. Mais le bouton ne montre rien du travail derrière la classe : sa définition, sa documentation et son entretien. C’est cette distance qui m’interpelle. Au moment où j’utilise le résultat, je peux oublier complètement le projet qui l’a rendu possible et la manière dont son équipe finance ses journées.

Pour moi, le témoignage invite à réexaminer le trajet complet. J’arrive avec un besoin d’interface, je demande une solution, j’obtiens du code. Si ce trajet contourne la documentation, la rencontre avec l’offre commerciale peut aussi disparaître. Wathan décrit précisément cette dépendance dans son entreprise. Cela suffit à poser une question économique sérieuse, sans avoir besoin d’en faire une règle pour tous les projets libres.

Je voudrais garder un réflexe simple quand une dépendance compte dans mon travail : connaître aussi les gens qui la maintiennent et ce qu’ils proposent pour soutenir leur activité. Cela peut entrer dans une discussion de budget au même titre que les autres outils du projet. Je ne veux pas attendre qu’un outil manque pour me demander comment il tenait jusque-là. Son utilité mérite une place dans cette réflexion, même quand son code est accessible gratuitement.

Le code libre a toujours besoin de moyens.

C’est cette facture qui me reste en tête après le témoignage de Wathan. Utiliser un framework plus facilement ne finance pas son entretien. Dans la situation qu’il décrit, le succès technique ne suffit plus à assurer l’équilibre économique de l’entreprise qui le porte.

Je m’inquiète de voir le financement devenir moins visible alors que l’outil reste présent dans le travail des développeurs. Si nos habitudes pour apprendre et écrire du code changent, il faut aussi pouvoir faire évoluer les moyens de soutenir ses auteurs. Le cas de Tailwind me ramène à cette question très concrète : qui paie le travail dont nous profitons ? J’ai envie que les outils que j’utilise puissent durer, avec les moyens de les maintenir.

Un outil utile a aussi une équipe.

Quand je parle du coût de mes outils, je veux y inclure ceux dont le code est libre. La gratuité d’accès ne dit rien du temps nécessaire pour les faire durer.
